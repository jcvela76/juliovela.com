# Julio Vela Project Instructions

## 1. Project Mission
Create a clean, practical foundation for `:// JULIO VELA` (TECH SOLUTIONS) as a personal technology brand focused on practical AI guidance, automation, software strategy, web/software solutions, and technology recommendations.

## 2. Brand Direction
- Brand identity: `:// JULIO VELA` + `TECH SOLUTIONS`
- Voice: practical, technical, clear, modern, minimal, non-hype
- Visual direction: minimal, modern, bold, clean, practical technology language
- Palette references:
  - Signal Red: `#E11D2E`
  - Space Gray: `#1F2329`
  - Graphite: `#2B2F36`
  - Interface Gray: `#9AA0A6`
  - Soft White: `#F5F6F7`
  - White: `#FFFFFF`

## 3. Technical Direction
Future implementation direction is Next.js App Router, TypeScript, Tailwind CSS, Framer Motion (where useful), MDX for articles, and Vercel hosting with preview-first review.

## 4. Content Direction
Favor practical, reusable content that can appear both on blog and LinkedIn, with explicit draft states, clear metadata, and approval gates.

## 5. Approval Rules
- Work doc-first.
- No publishing automatically.
- Never publish content without Julio’s explicit approval.
- LinkedIn publication requires explicit approval.
- Blog publication requires explicit approval.
- Never deploy to production automatically.
- Never modify DNS automatically.
- Content generated by humans or AI tooling starts as draft.
- Production changes require explicit user approval.

## 6. Security Rules
- Never create or commit secrets.
- Never edit `.env` files with real values.
- Use `.env.example` only for documentation.
- Do not print tokens, API keys, webhook secrets, or credentials.
- Keep secrets in local environment, Vercel dashboard, n8n credential manager, or a secure secret manager.

## 7. Development Rules
- Keep changes small and reversible.
- Prefer project-local tooling, configuration, and lockfiles.
- Do not modify system Node, pnpm, npm, Python, Docker, or global runtimes.
- Do not install global tools.
- Use the project runtime only in the active working terminal/session.
- When a Node or pnpm version is required, use the project-local toolchain declared in `.mise.toml`, `.node-version`, `.nvmrc`, and `package.json`.
- Prefer `mise exec -- pnpm ...` for project commands so the correct Node/pnpm versions are used without changing global machine versions.
- Do not run commands that change the user's global/default Node, npm, or pnpm versions.
- If the required local runtime is unavailable, document the setup blocker and exact local command to run instead of installing or switching global versions.
- Keep the repository clean and auditable.

## 8. Testing and Quality Rules
- Every implementation task requires validation before handoff.
- Include validation results for each task.
- For implementation work, require: lint, typecheck, tests, build, and content checks as applicable.
- During live UI iteration, every code change must be followed by at least:
  - `mise exec -- pnpm lint`
  - `mise exec -- pnpm test`
- Before final handoff or commit recommendation, run the full default validation suite.
- If a dev server is running, be aware that `next build` can rewrite `.next`; after a full build, verify the dev preview and restart or move ports only with user approval.
- Every code or configuration change must end with the default validation suite before handoff whenever dependencies are available:
  - `mise exec -- pnpm lint`
  - `mise exec -- pnpm typecheck`
  - `mise exec -- pnpm test`
  - `mise exec -- pnpm build`
  - `mise exec -- pnpm check:all`
  - `git diff --check`
  - `git status --short --branch`
- Never mark validation as passed unless every required command above succeeds.
- If one check fails, fix only scope-safe issues in this slice and rerun the full suite.
- If a required check is blocked by environment issues (for example DNS/registry when installing deps), report it as BLOCKED and do not mark the change ready to commit.
- Do not commit implementation code until validation passes.

## 9. Docker and Port Safety
- Before using Docker, check active ports with `lsof` and `docker ps`.
- Keep reserved port strategy documented to avoid conflicts.
- Do not run containerized services without pre-checking port availability.

## 10. Vercel and Deployment Rules
- Use Vercel preview deployments for feature branches and PRs.
- Production is only for approved states and explicit user approval.
- Do not deploy to production automatically.
- DNS/domain updates require explicit user approval.
- Validate builds and checks before deployment review.

## 11. Content Publishing Rules
- Generated content remains draft until approved.
- Approved workflow: `idea` → `draft` → `ready_for_review` → `approved` → `published` → `archived`.
- No auto-posting, no auto-publishing.

## 12. Expected Handoff Format
Each Codex handoff must include:
- Files created
- Files updated
- Commands run
- Validation performed
- Assumptions made
- Risks or follow-ups
- Suggested next commit message
- Current git status
